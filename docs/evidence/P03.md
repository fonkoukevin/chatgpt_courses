## Contraintes réellement établies

Une identité COURSE/MODULE/ACTIVITY est stable ; un titre et un slug ne sont pas une identité. Slug unique par type/langue ; traduction unique par version/langue. Les pointeurs de révision courante/publiée appartiennent par FK composite à leur propre traduction. Une correction ajoute un instantané éditorial ; de nouveaux objectifs/évaluations nécessitent une nouvelle version pédagogique.

Versions et compositions se gèlent irréversiblement après construction, enfants avant parent. Révisions éditoriales append-only, FK métier RESTRICT, attributions de permissions conservées par révocation. Le verrou de ligne du parent protège aussi l’ajout concurrent d’une composition lors du gel. Les dates incohérentes/non finies et révisions hors bornes sont refusées.

Les conventions d’écriture sont préparées et testées : 428 sans révision requise, 412 pour révision dépassée/conflit optimiste, 400 pour If-Match malformé, 409 pour conflit de contrainte. Listes de tags par OU et comparaison forte ; `*` seul ne satisfait pas la politique de **révision explicite** et reçoit 428, même s’il possède une sémantique HTTP d’existence valide. Le helper n’est pas un verrou : les futurs cas d’utilisation doivent l’appeler après autorisation dans leur transaction, puis écrire avec `@Version`/UPDATE conditionnel. Aucune mutation métier complète n’est annoncée déjà intégrée.

La politique d’accès refuse les contextes inconnus, l’absence de session active, une propriété différente ou un droit/une permission non confirmé. Les données personnelles sont séparées des droits pédagogiques. Un rôle ADMIN seul ne donne pas une permission spécifique. Cette abstraction interne ne remplace pas les filtres Spring existants ni les prochains services métier ; ses snapshots ne sont pas des DTO d’autorité acceptés du navigateur.

Les erreurs sont `application/problem+json`, `type` explicite, code stable, trace UUID, champs d’erreur sûrs et `private, no-store`, sans valeur rejetée ni exception SQL dans le corps. Les montants futurs restent des entiers en unités mineures avec devise explicite ; aucun prix, taux, durée d’accès ou support commercial n’a été choisi.

## Défauts observés puis corrigés

1. **Format Problem** : la première suite signalait quatre erreurs. Diagnostic ciblé exécuté : les extensions étaient déjà à la racine ; c’est `type` qui était omis par Spring 7.0.10. Notre contrat l’exige explicitement. `ApiProblems` le fixe à `about:blank`, assertions conservées. Cinq tests HTTP ciblés puis les 24 tests globaux passent. Ce choix respecte notre contrat sans prétendre que l’omission initiale était une violation du RFC. [Source Spring correspondant à l’artefact](https://raw.githubusercontent.com/spring-projects/spring-framework/v7.0.10/spring-web/src/main/java/org/springframework/http/ProblemDetail.java).
2. **Suppression RESTRICT** : deux assertions attendaient 23503 ; PostgreSQL 18 renvoie précisément **23001/restrict_violation**. Assertions corrigées au code observé/documenté, DDL inchangée. Le refus et le type RESTRICT sont toujours vérifiés. [Codes PostgreSQL 18](https://www.postgresql.org/docs/18/errcodes-appendix.html).
3. **Import après gel** : revue du trigger BEFORE INSERT et d’ON CONFLICT. Le loader évite aussi l’INSERT d’une composition déjà existante, pour qu’un parent gelé ne fasse pas échouer un replay sans modification. Test réel ajouté au scénario de replay.
4. **Reproductibilité du client** : hash du YAML normalisé UTF-8/LF pour les checkouts Windows/Linux, preuve CRLF exécutée. Le transport généré expose les données inconnues comme `unknown` et garde ses assertions génériques à une frontière bornée ; transformation exacte rejetée si le gabarit change, sans désactivation de lint.
