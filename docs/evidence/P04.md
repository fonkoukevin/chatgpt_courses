## Règles et limites établies

Email : espaces de bord retirés, minuscules, validation et limite de 320 caractères ; points et suffixes `+` conservés. Nouveau mot de passe : 12 à 128 points de code Unicode, au plus 1024 octets UTF-8. Encodage versionné `{pbkdf2@SpringSecurity_v5_8}` : PBKDF2-HMAC-SHA256, 310000 itérations, sel 16 octets, sortie 256 bits. Hash transitoire dans le principal et credentials effacés ; aucune clé d’authentification en localStorage. Les propriétés JSON inconnues sont refusées, notamment rôle/propriétaire fournis dans un formulaire.

Le login URL-encodé passe par Spring et change l’identifiant de session. Le principal/index JDBC utilise l’UUID stable ; chaque requête authentifiée recharge compte actif, version d’authentification et permissions. Une désactivation ou une version devenue ancienne invalide la session ; une permission retirée interdit le vrai PATCH de préférences dans la même session. GET/PATCH déduisent le propriétaire du principal ; PATCH vérifie permission, If-Match et concurrence JPA dans la transaction. Les autres fonctions privées ne sont pas réputées intégrées par ces contrôles.

Cookie `SESSION` HttpOnly/SameSite=Lax/Path=/, sans Domain partagé, Secure piloté par la configuration runtime validée. HTTP local et production HTTPS restent distincts. Spring CSRF conserve son dépôt de session, le chargement différé et le masquage XOR/BREACH ; aucune désactivation globale. Le jeton reste en mémoire frontend, renouvelé après login/logout/reset ou 401/403 ; aucune mutation n’est rejouée automatiquement. Lectures SSR : origine API interne configurée, cookie SESSION uniquement, `no-store`. Les réponses privées et Problem ne passent pas dans un cache partagé.

L’API écoute en boucle locale, avec `forward-headers-strategy=none`. URL de récupération construite uniquement depuis `APP_PUBLIC_ORIGIN`, jamais Host ou X-Forwarded-Host fournis par le client. Le token de 32 octets aléatoires devient 43 caractères base64url ; seule son empreinte SHA-256 est stockée, avec échéance 30 minutes. Trois demandes par email normalisé sur quinze minutes ; les clés de quota sont hachées. Compte inconnu/désactivé ou quota dépassé conservent la réponse 202 vide. Consommation unique et incrément de version sous verrou du compte ; tous les jetons inutilisés et sessions du compte sont révoqués. Le navigateur de reset est lui aussi déconnecté puis recharge CSRF.

Le lien utilise un fragment `/fr/reinitialisation#token=…` ou `/en/reset-password#token=…`, retiré de l’historique par l’interface ; aucune URL complète ou production privée n’est enregistrée comme preuve. La livraison P04 est asynchrone en mémoire : un arrêt avant livraison peut perdre une notification. Aucun SMTP externe, délivrabilité, recette de proxy HTTPS ou production observée n’est validé ici.

Le brouillon d’essai est facultatif, non sensible, conservé dans `sessionStorage` deux heures, sans `userId` ; restauration volontaire après login. Aucun import serveur fictif dans un projet ou une méthode dont le service n’existe pas encore. Logout purge les caches personnels de l’application sans supprimer les données du compte. ## Défauts observés et corrections

1. Revue de concurrence : l’émission d’un lien pouvait lire une ancienne version d’authentification pendant un changement concurrent de credentials, produisant un lien immédiatement inutilisable. Émission et consommation prennent désormais le même verrou du compte. Un sixième test observe l’attente du verrou PostgreSQL, puis vérifie l’époque validée et une consommation réussie. Le ciblé six tests puis le global final de 37 tests passent.
2. Lint React : un défaut d’immutabilité lié à une fabrique `useMemo` a été corrigé avant le lint global réussi, sans désactivation de règle.
3. Première recette Chromium : `getByLabel(..., { exact: true })` ne correspondait pas aux labels requis décorés d’une étoile. Les treize scénarios ont échoué. Playwright inclut ici l’étoile masquée dans le texte du label ; sélecteurs corrigés sans changer les noms accessibles ni retirer les assertions de focus. Les deux passages suivants réussissent.
4. Revue du reset : le lien de langue courante pouvait réintroduire le fragment déjà retiré. Il conserve maintenant l’URL canonique sans jeton ; l’autre langue reçoit le fragment pour son prochain montage. Le dernier passage vérifie ces deux liens et le clic sur la langue courante.
