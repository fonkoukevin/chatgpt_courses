# Candidat de bootstrap privé — non publié, non exécuté

Ce dossier est un candidat pour le futur dépôt **privé** `fonkoukevin/chatgpt_courses_registry`. Sa création et tout envoi restent à autoriser. Ne pas copier le dépôt applicatif : uniquement les fichiers de ce candidat, sans ses éventuels rapports `.runtime/`.

Le workflow est exclusivement manuel, avec `plan` par défaut. Il n'utilise ni npm, PAT, secret durable, SSH, environnement de déploiement, ni source applicative. `plan` possède seulement `contents:read` et `packages:read`. `bootstrap` exige son opt-in explicite et utilise le `GITHUB_TOKEN` éphémère avec `packages:write`.

Périmètre fixe : `ghcr.io/fonkoukevin/chatgpt_courses-private/web` et `/api`. Le dépôt doit être privé, non forké, sur le commit courant de `main`. Les deux routes de métadonnées de chaque paquet doivent répondre404 et la lecture anonyme être refusée de façon structurée. Un200, y compris pour un paquet privé, ou un403/état ambigu bloque avant credentials, build ou push. Le paquet web actuellement public bloque donc ce candidat ; aucune suppression n'est incluse. Son traitement nécessite une autorisation distincte de celle de l'ancien paquet déjà supprimé.

En cas de création autorisée, Docker reçoit seulement deux fichiers aux octets vérifiés dans un contexte temporaire : `FROM scratch` et un marqueur inerte fixe. Aucun code, configuration ou credential applicatif. Le token arrive uniquement par stdin au login, dans un Docker config temporaire vérifié ; le workflow possède un trap de logout/nettoyage borné sans suppression récursive. `BUILDX_CONFIG` possède son propre répertoire temporaire vérifié et transmis explicitement à Docker, pour éviter qu'un état Buildx sous le dossier d'authentification empêche son nettoyage. Un état Buildx résiduel est laissé au runner GitHub jetable ; aucun cache préexistant n'est lu ou effacé. Les commandes Docker sont silencieuses. Aucun manifeste de release applicative n'est produit.

Avant chaque push, le paquet doit rester absent pour ce jeton. Après chaque push, le script relit son digest, exige métadonnées privées et source privée de bootstrap, puis refus anonyme. Le reçu conserve les stades et flags de push ; un échec partiel impose revue, sans retry, suppression ou reprise automatique. Un web créé mais API échoué bloquera le prochain bootstrap puisqu'il exige les deux destinations absentes. Une réponse perdue peut laisser un stub créé sans confirmation.

Limites :404 est limité aux droits du jeton, pas une preuve globale d'absence d'un paquet privé invisible. Les contrôles sont ponctuels ; les modifications concurrentes ne sont pas exclues. Les traps ne garantissent pas le nettoyage après SIGKILL/perte du runner ; le jeton expire avec le job. Les tests locaux simulent réseau/Docker et ne démontrent ni création GHCR privée ni nettoyage Linux réel.

La [documentation spécifique Actions](https://docs.github.com/en/packages/managing-github-packages-using-github-actions-workflows/publishing-and-installing-a-package-with-github-actions) décrit un héritage du modèle de visibilité à la création avec `GITHUB_TOKEN`, tandis que la [documentation générale](https://docs.github.com/en/packages/learn-github-packages/configuring-a-packages-access-control-and-visibility) distingue permissions et visibilité. Cela explique la prudence de ce candidat ; aucune confidentialité n'est annoncée avant observation réelle.

Après bootstrap privé vérifié seulement, la [migration de liaison vers le dépôt source public](https://docs.github.com/en/packages/learn-github-packages/connecting-a-repository-to-a-package) et les permissions Actions nécessiteront les réglages UI. Aucun relink ou octroi d'accès n'est automatisé ici. Il faudra conserver les accès granulaires, ne pas activer l'héritage public, puis revérifier visibilité/refus anonyme/source. GitHub avertit que donner à un dépôt public accès à un paquet privé peut permettre l'accès à ses forks : ce risque doit être décidé avant tout octroi, même si le refus anonyme passe. Le garde applicatif actuel restera bloquant tant que la source et la confidentialité ne concordent pas.
