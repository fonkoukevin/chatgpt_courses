# Recettes navigateur P01 à P12 — intégration locale

Ce scénario utilise Playwright et un Chromium dédié, sans prendre le contrôle du navigateur personnel. L’utilisateur a explicitement autorisé cette méthode le 8 novembre 2026. La recette finale a été exécutée : **sept tests réussis, aucun échec, aucun test ignoré**, puis les 16 captures ont été examinées. Les preuves sont dans [l’index de recette](../../docs/evidence/P01-browser/README.md).

`@playwright/test` **1.65.0** est une dépendance de développement exacte dans le lockfile unique. `courses ci` la réinstalle ; `courses run browser:install` installe explicitement son Chromium dans `.tools/playwright`. Le superviseur de recette ne télécharge aucun navigateur et ne lance aucun `npx` susceptible d’installer un paquet automatiquement.

Commandes Windows, après `npm ci` via le wrapper et builds web/API : `.\scripts\courses.cmd run browser:install`, puis `run typecheck:browser` et `run verify:browser`. PostgreSQL local doit être démarré et `.env.local` renseigné ; aucune donnée n’est réinitialisée.

Le superviseur réserve les ports **3101 et 8181** par défaut (`BROWSER_WEB_PORT` et `BROWSER_API_PORT` permettent un autre choix), puis démarre le JAR existant et le build Next sur la boucle locale. Il refuse un port occupé et ne réutilise ni n’arrête les services de développement en 3000/8080. Il enregistre ses seuls PID dans `.runtime/browser-<session>/processes.json`. L’arrêt/reprise de Spring passe par un IPC privé authentifié, sans endpoint produit de simulation.

Les sept tests P01 couvrent FR/EN à 1440, 390 et 320 px : navigation clavier, cible du lien d’évitement, focus visible conservé après réponse, réponse réelle Spring/PostgreSQL, erreur 404 structurée, absence de défilement horizontal et d’exception JavaScript. Le dernier test arrête réellement Spring, vérifie l’indisponibilité dans les deux langues pendant que Next répond toujours, redémarre Spring, puis utilise « Réessayer » pour confirmer la reprise et le transfert de focus attendu.

Depuis P06, ces contrôles techniques ouvrent `/{locale}/dev/foundations` ; l’accueil lit le catalogue publié. Les recettes P05 à P11 réservent leur propre PostgreSQL en tmpfs, sans employer le volume Compose. Elles créent leurs comptes et publications fictives dans cette seule instance, contrôlent son étiquette d’appartenance et l’arrêtent après les tests. Aucun compte éditeur ni contenu public n’est injecté dans la base de développement partagée.

P09 a réussi ses huit scénarios finaux ; P10 ses douze scénarios complets. Les résultats et limites restent dans [P09](../../docs/evidence/P09.md) et [P10](../../docs/evidence/P10.md), sans validation de stockage, de courrier ou de fournisseur vidéo en production.

P10 utilise `scripts/lib/browser-services.mjs` pour créer et arrêter ses seuls conteneurs S3/Mailpit, sur des ports de boucle locale attribués par Docker. Les étiquettes de session sont revérifiées avant arrêt ou pause. Le stockage réserve la capacité pour les deux buckets et le journal du filer ; il ne réutilise ni les identifiants ni les volumes S3 de développement. Le MP4 de test est importé explicitement dans un répertoire privé temporaire, sans prétendre qu’un film de formation a été produit. Le navigateur contrôle transfert CORS, confirmation canonique, téléchargement propriétaire, image publique, décodage et Range vidéo, positions FR/EN indépendantes, permissions et données expurgées des notifications. Une inscription réelle pendant la pause du seul Mailpit isolé produit un envoi indéterminé ; la reprise exige motif et risque de doublon, puis vérifie un unique message et le refus d’une nouvelle reprise d’un envoi accepté. Aucun état d’email n’est fabriqué en base.

P12 réemploie ces services isolés et ajoute `scripts/lib/browser-payments.mjs`. Le serveur de recette contrôle uniquement les réponses distantes du SDK Stripe et signe ses événements synthétiques ; leur réception passe par le vrai proxy Next, la signature SDK, l’inbox PostgreSQL, le rapprochement et les transactions d’attribution. Ses secrets de test restent en mémoire. La première interruption conserve l’inbox dans PostgreSQL puis redémarre réellement le processus Spring avec le worker activé. Le contrôle privé IPC ne devient jamais une route produit. La navigation vers une URL Checkout synthétique HTTPS est interceptée dans le seul contexte Chromium de recette, sans contacter Stripe. Les résultats et limites réellement observés sont dans [P12](../../docs/evidence/P12.md) ; cette recette ne remplace pas le parcours fournisseur avec clés de test.

Sur la reprise P12, un démarrage à froid Spring de 202 secondes a été observé. Le superviseur attend donc au plus 300 secondes la disponibilité P12, avec IPC de 360 secondes ; les assertions restent actives et les retries Playwright restent à zéro. Le premier scénario dispose de 480 secondes pour le redémarrage et l’incident réel d’activation ; la suite est bornée à vingt minutes. La vérification HTTP générale utilise également un délai de préparation de 300 secondes. Ces délais concernent la préparation locale, pas les timeouts réseau de l’application.

Les rapports des lots ultérieurs utilisent `docs/evidence/Pxx-browser/<session>/`. Les captures P06–P10 placent le focus sur le contenu principal avant photographie pour éviter un artefact du lien d’évitement ; les assertions de clavier sont réalisées séparément. Les cartes de notifications ont aussi des captures de détail, car une très longue page peut être réduite par l’outil de revue. Les diagnostics S3 joints aux cas CMS ne conservent que méthodes, statuts, codes réseau et booléens CORS, sans URL signée ni réponse XML. Le contrôleur IPC arrête uniquement l’API réservée à la recette et met en pause/reprend son Mailpit isolé, jamais les onglets ou serveurs personnels. Ne pas lancer deux recettes sur les mêmes ports en parallèle.

Les captures PNG de page, sans barres du navigateur utilisateur, et le rapport JSON vont dans `docs/evidence/P01-browser/<session>/`. La capture remonte au début de page sans changer le focus, pour éviter un artefact des éléments fixes après défilement. Les résultats temporaires et journaux restent dans `.runtime/`. Chaque exécution possède son dossier. Un code de sortie non nul ou un nettoyage non confirmé reste un échec ; tous les arrêts sont tentés et regroupés dans l’erreur finale. Les images sont ensuite examinées : les assertions automatiques ne suffisent pas à déclarer une revue visuelle.
